# «Бытовая магия» — 1.1.1

Постоянный preview: https://pwa-prototype.byitovaya-magiya.pages.dev/

Ветка pwa-prototype. Main не меняется, PR остаётся draft.

## Изменения

- Универсальные напоминания полностью удалены из интерфейса и обработчиков. Legacy reminders сохраняются в модели только для совместимости загрузки, импорта и экспорта 1.1.0. Пользовательских текстов про будущие уведомления нет.
- Окно PNG: «Карточка готова», изображение, одна кнопка «Поделиться карточкой», закрытие. Кнопка проверяет поддержку файлов Web Share; иначе скачивает PNG. При отмене Share Sheet ничего не скачивается. При отказе API используется тот же fallback. Текстовый вариант остался в коде на случай невозможности генерации картинки и в подробной карточке, но не отдельной кнопкой PNG-окна.
- Крупные поверхности статистики, «Следующее по плану», статусов и карточки «Поколдовано» стали светлыми; кнопка случайного выбора — чёрная. Жёлтый остался на маленьких иконках, метке даты и декоре, розовый — основной яркий акцент.
- Случайный блок: «ЧТО-НИБУДЬ НА СЕГОДНЯ», «Выбрать ритуал» / «Выбрать другой ритуал», без объяснения внутренней фильтрации. Сам отбор по дате, фазе и контексту не изменён.
- В standalone кнопки установки нет. В обычной странице — «Добавить на главный экран» с прежней инструкцией.
- Проверка обновлений сообщает «Новых обновлений нет» или показывает плашку с основным «Обновить». При наличии данных плашка говорит «Ваш журнал сохранится автоматически» и предлагает необязательное скачивание копии.

## Что подтверждено о потере журнала

В 1.1.0 был небезопасный путь запуска:

1. load() ловил любую ошибку чтения/JSON/normalise и возвращал normalise({}).
2. Затем стартовый код ещё раз проверял наличие STORE и безусловно записывал туда полученный state.
3. Если исходный ключ существовал, а нормализация не удалась, пустое состояние могло заменить старый журнал.

tests/storage.cjs использует настоящий стартовый фрагмент 1.1.0 и смоделированный отказ normalise на валидном непустом журнале. Он воспроизводит исчезновение log и favorites. Это доказательство дефекта кода, а не установление причины конкретного эпизода на физическом iPhone. Точное событие на устройстве без данных до/после и диагностического лога недоступно; утверждать, что там сработал именно этот путь, нельзя. Обычная корректная нормализация здорового state в прежних тестах сохраняла данные.

Переход на другой адрес preview, очистка данных Safari или другой профиль/контекст хранения также не являются обычным обновлением той же установки. Автоматического переноса между такими хранилищами нет. Для переноса доступен JSON. Этот раунд исправляет дефект записи на прежнем origin и не выдаёт смену адреса за подтверждённую причину вашего случая.

## Безопасное хранение

Ключ bbm-pwa-v1 и schemaVersion: 2 сохранены. Новый storage.js отделяет загрузку, запись и checkpoint перед обновлением.

- Загрузка не записывает state обратно в STORE вообще. Поэтому пустой fallback не может затереть журнал при запуске.
- После JSON-парсинга проверяется форма результата и сохранность всех распознаваемых log/favorites, булевых настроек и onboarding. Несовместимая будущая схема или потеря записей в normalise блокирует запись.
- Повреждение отдельного поля не уничтожает другие корректные поля. Неизвестные поля игнорируются моделью; исходная строка не перезаписывается при загрузке.
- Есть один ограниченный резервный ключ bbm-pwa-v1-backup. Он хранит предыдущую прочитанную корректную строку перед изменением, а перед обновлением — текущую сохранённую строку. Это не бесконечная история версий.
- Если основной JSON повреждён, но внутренняя копия читается, журнал загружается из неё. Если читать/мигрировать нечего, приложение не показывает фиктивную нулевую статистику в «Моё», сообщает о проблеме и предлагает повторить загрузку или импорт. Записи из пустого fallback заблокированы.
- Изменение данных другим окном обнаруживается сравнением сохранённой строки. Устаревшее окно не перезапишет свежие данные; действие нужно повторить после загрузки актуального журнала.
- Ошибка/quota при записи не вызывает clear/removeItem. Основной ключ не удаляется; сбой резервирования не делает экспорт обязательным и не очищает журнал.
- Намеренная подтверждённая замена импортом остаётся возможной, включая пустую корректную копию. Пустой основной state после такой замены не воскресит старый backup при следующем запуске.

Service worker удаляет только старые bbm-shell-* в Cache Storage. Пользовательское хранение от этого независимо. В новом shell 14 файлов, включая storage.js; navigation Response по-прежнему берётся из корня и не имеет redirected=true.

## Проверки

- Content/model: 26 ритуалов и календарь не менялись; допустимость случайного выбора проверена на 730 датах; старые экспорты и legacy reminders принимаются; merge/replace, повреждённые и пустые состояния проверены.
- Storage: воспроизведение старого дефекта, отказ normalise, пустой результат normalise, временный отказ чтения, будущая схема, частично повреждённые поля, внутренняя копия, ошибочная запись/quota, устаревшее окно, legacy ключ, отсутствие записей при load.
- Реальный клиент из fixtures/v1.1.0: HTML/app/model/SW → новая версия через waiting worker, кнопку и reload. 4 log / 3 monthly / 3 favorites / settings / onboarded / 2 reminders сохраняются, primary строка побайтно прежняя. Следующее обновление моделируется ответами сервера: новая плашка, необязательная копия, checkpoint, reload, offline.
- Chromium UI: 4 раздела, поиск/категории/детали, отсутствие напоминаний и лишних PNG-действий, единая отправка и fallback, отмена/отказ share, импорт/экспорт/merge/replace, генерация обеих PNG 1080×1920, offline, размеры 320–1280, текст кнопок, отсутствие JS page errors.
- standalone смоделирован для проверки отсутствия установки; iPhone user-agent — для текста инструкции. Это не физический Safari/iOS.

## Ограничения и ответ про переустановку

Нет — удалять установленную PWA после обычного обновления на том же адресе не нужно. Версия применяется поверх прежней установки без очистки журнала. Внутренняя копия не заменяет внешний экспорт при очистке всех данных сайта, переезде на другой origin или удалении браузерного хранилища системой. Уже стёртые данные без сохранившейся копии восстановить невозможно.

Проверки выполнены в Chromium; физический iPhone, Share Sheet и Safari file picker недоступны для моей самостоятельной проверки. Их нужно подтвердить по чек-листу выше. Web Push, серверная часть и синхронизация не добавлены.
